🧭 How SQL evaluates a query

1FROM / JOINwhich tables?
2WHEREfilter rows
3GROUP BYbuild groups
4HAVINGfilter groups
5window functions… OVER (…)
6QUALIFYfilter on window results

So: SELECT aliases are unknown in WHERE; WHERE can't use aggregates.

📊 Aggregate – GROUP BY · HAVING

SELECT p.product_name, SUM(l.quantity) AS units_sold
FROM silver.sales_order_line AS l
INNER JOIN silver.product AS p
    ON l.product_id = p.product_id
WHERE l.quantity > 0           -- rows, before grouping
GROUP BY p.product_name
HAVING SUM(l.quantity) < 5000  -- groups, after

Other columns go into GROUP BY (or GROUP BY ALL). Aggregates ignore NULLs.

COUNT(DISTINCT order_id)
    FILTER (WHERE sales_channel = 'Online')   AS online,
SUM(gross_revenue_eur)
    FILTER (WHERE sales_channel = 'In-store') AS cafe

FILTER (WHERE …): several conditional KPIs in one pass.

➕ Subtotals – ROLLUP · CUBE

SELECT s.store_name, p.product_category,
       SUM(f.gross_revenue_eur)     AS revenue_eur,
       GROUPING(p.product_category) AS is_store_total
FROM gold.fact_coffee_sales AS f
INNER JOIN gold.dim_store AS s
    ON f.store_key = s.store_key
INNER JOIN gold.dim_product AS p
    ON f.product_key = p.product_key
GROUP BY ROLLUP (s.store_name, p.product_category)

ROLLUP (a, b) → (a, b) · (a) · total  |  CUBE (a, b) → (a, b) · (a) · (b) · total  |  GROUPING(col) = 1: this NULL means "all values".

🔗 Joins – combine columns from several tables

INNER JOIN
only rows with a partner on both sides		order lines × products – unknown SKUs drop out
LEFT JOIN
all left rows; NULL where no partner		sales × loyalty cards – guests stay in the fact
FULL OUTER JOIN
everything from both sides		CRM × web accounts – café-only, online-only, both
LEFT SEMI JOIN
left rows with a match – left columns only, never duplicated		lines of completed orders · = WHERE EXISTS
LEFT ANTI JOIN
left rows without a match		lines of voided receipts, members who never bought · = NOT EXISTS
CROSS JOIN
every combination, no ON		store × day grid – find days without sales
FROM silver.sales_order_line AS l
INNER JOIN silver.sales_order AS o
    ON l.order_id = o.order_id
LEFT JOIN silver.product_price AS pp    -- range join: the price
    ON  l.product_id = pp.product_id    -- valid on the order date
    AND o.order_date BETWEEN pp.valid_from
        AND COALESCE(pp.valid_to, DATE'9999-12-31')

🧯 Join pitfalls

  1. Silently lost rows – an INNER JOIN drops rows without partner. Compare COUNT(*) before and after.
  2. Messy keys – case, blanks, types. Normalize first: LOWER(TRIM(email)), CAST(id AS INT). NULL keys never match.
  3. Fan-out – several rows per key on the right side duplicate the left rows (and double the revenue). Make the right side unique first (QUALIFY, GROUP BY).
  4. LEFT JOIN turned INNER – a WHERE condition on the right table removes the NULL rows again. Put it into ON.

✅ Prove your gold layer

-- ① the primary key is unique                  → 0 rows
SELECT customer_key FROM gold.dim_customer
GROUP BY customer_key HAVING COUNT(*) > 1;
-- ② every fact row finds its dimension row      → 0 rows
SELECT * FROM gold.fact_coffee_sales AS f
LEFT ANTI JOIN gold.dim_customer AS d
    ON f.customer_key = d.customer_key;
-- ③ nothing lost on the way: totals match       → equal
SELECT SUM(quantity)      FROM silver.sales_order_line;
SELECT SUM(quantity_sold) FROM gold.fact_coffee_sales;
-- ④ new table = old table, in both directions   → 0 rows
SELECT * FROM new_table MINUS SELECT * FROM old_table;
SELECT * FROM old_table MINUS SELECT * FROM new_table;

🧱 WITH … AS – name your building blocks

WITH active_card AS (
    SELECT customer_id, loyalty_tier
    FROM silver.loyalty_card
    WHERE is_active
),
orders AS (
    SELECT customer_key, COUNT(DISTINCT order_id) AS n
    FROM gold.fact_coffee_sales
    GROUP BY customer_key
)
SELECT c.customer_id, a.loyalty_tier, o.n AS orders
FROM silver.customer AS c
LEFT JOIN active_card AS a
    ON c.customer_id = a.customer_id
LEFT JOIN orders AS o
    ON c.customer_id = o.customer_key

Read top to bottom · one question per CTE · test each block alone.

🌳 WITH RECURSIVE – hierarchies

WITH RECURSIVE org (employee_id, full_name, level) AS (
    SELECT employee_id, full_name, 1      -- ① anchor
    FROM silver.employee
    WHERE manager_id IS NULL
    UNION ALL
    SELECT e.employee_id, e.full_name, o.level + 1  -- ②
    FROM silver.employee AS e
    INNER JOIN org AS o ON e.manager_id = o.employee_id
)
SELECT * FROM org ORDER BY level

Stops when a step finds no new rows. Small, fixed depth? Self-joins are enough.

👤 The unknown member

SELECT customer_key, loyalty_segment, city
FROM known_customers
UNION ALL
SELECT -1, 'Guest', 'Unknown'  -- "we don't know"

Facts get COALESCE(customer_key, -1) → no lost rows, a Guest bucket in reports.

🪟 Window functions – look at other rows

FUNCTION(…) OVER (PARTITION BY <group> ORDER BY <order>)
ROW_NUMBER()1, 2, 3 … per partition – dedupe, "first order"
RANK() · DENSE_RANK()rankings with ties (1, 1, 3 · 1, 1, 2)
SUM(x) OVER (PARTITION BY g)group total next to every row
SUM(x) OVER (… ORDER BY d)running total
LAG(x) · LEAD(x)value of the previous · next row
SELECT *                         -- latest CRM version
FROM bronze.crm_customers
QUALIFY ROW_NUMBER() OVER (PARTITION BY customer_id
                           ORDER BY updated_at DESC) = 1

Unlike GROUP BY, window functions keep every row. QUALIFY filters on them like HAVING filters on aggregates.

🧰 Functions for the gold layer

EXPLODE · POSEXPLODE one row per array element (+ position)
SELECT order_id, POSEXPLODE(items) AS (item_pos, item)
FROM bronze.web_orders

EXPLODE(SEQUENCE(d1, d2, INTERVAL 1 DAY)) = one row per day · empty arrays vanish → EXPLODE_OUTER

COALESCE first value that is not NULL
COALESCE(lc.customer_id, wc.customer_id, -1) AS customer_key,
COALESCE(discount_eur, 0)                     AS discount_eur

defaults and "first source that knows it"

CASE · IFF rules – the first true WHEN wins
CASE WHEN total_orders = 0    THEN 'Prospect'
     WHEN total_orders >= 100 THEN 'Loyalist'
     WHEN total_orders >= 10  THEN 'Regular'
     ELSE 'Occasional' END,
IFF(is_online, 'Online', 'In-store')

no ELSE → NULL · IFF for exactly two outcomes

DECODE translate codes – a compact lookup CASE
DECODE(payment_code, 'B', 'Cash', 'G', 'Girocard',
                    'K', 'Credit Card', 'Unknown')

always give a default – new codes stay visible

MAX_BY · MIN_BY the value at the maximum / minimum
MAX_BY(list_price_eur, valid_from) AS current_price,
MAX_BY(store_key, orders)          AS favourite_store_key

"latest", "current", "favourite" – without a self-join

DATEADD · DATEDIFF calculate with dates
CAST(DATEADD(DAY, -1, next_valid_from) AS DATE) AS valid_to,
DATEDIFF(DAY, last_purchase_date, current_date()) AS idle

DATEADD returns a TIMESTAMP → cast to DATE · month ends handled (31 Jan + 1 month = 28 Feb)
